# RollerBot — правила работы с проектом

Telegram-бот розыгрышей (`@roller_official_bot`) + мини-апп участия + веб-админка.
Прод: `/opt/giveaway-bot` на отдельном сервере, под pm2. Код — CommonJS, Node 20 на сервере.

Этот файл читается автоматически в начале каждой сессии. Здесь то, что **не видно из кода**:
запреты, грабли и договорённости. Всё остальное — в `README.md`.

---

## Запреты

**Не запускать бота локально.** `npm start`, `npm run dev`, `node src/index.js` — нельзя.
В локальном `.env` тот же `BOT_TOKEN`, что и на проде. Второй процесс с тем же токеном
вызывает у Telegram ошибку 409, и **боевой бот падает**. Это уже случалось.

**Не запускать `node --test src/`** (по каталогу) — подхватит лишнее и поднимет бота.
Только `npm test` или конкретные файлы: `node --test src/winner-notify-sync.test.js`.

**Не править код на сервере.** Сервер — чистая копия GitHub, пул только оттуда.
Ручная правка там потеряется при следующей выкатке и разведёт состояния.

**Не трогать в веб-админке ничего, кроме чтения.** Владелец делает все действия
через мини-апп; сайт — только статистика и поддержка. Единственное исключение:
в диалогах поддержки **должны** остаться ответ и завершение чата.

**Не писать пользователям.** Уведомления и тесты — только владельцу (`@timur_dollar`).

## Выкатка

```bash
npm test                       # локально, обязательно
git push origin main
ssh ... 'bash /opt/giveaway-bot/deploy/update.sh'
```

`update.sh` делает `git pull origin main` → `npm install --omit=dev` → `pm2 startOrRestart`.
GitHub — единственный источник правды для кода.

**Не в git и живёт только на сервере:** `.env` (токены), `data/giveaway.db` (вся база),
`data/uploads` (картинки постов), `backups/`.

## Резервные копии

Локальные копии в `backups/` лежат на том же диске, что и база, — от смерти машины
не спасают. Поэтому каждые 3 часа зашифрованная копия базы уходит **в Telegram**
владельцу: `scripts/backup-to-telegram.js`, systemd-таймер `giveaway-tg-backup.timer`.

Снимок снимается через `db.backup()` (штатный онлайн-бэкап SQLite) — обычная
копия живого файла может порваться на середине записи. Шифрование обязательно:
в базе id пользователей, юзернеймы и TRC-20 кошельки, а нешифрованная копия в
чате — это копия в чужом облаке. Пароль лежит в `.env` (`BACKUP_PASSPHRASE`),
сгенерирован на сервере и **нигде не печатается**.

Восстановление не требует ничего из этого репозитория:

```bash
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -in ФАЙЛ -out db.gz -pass pass:ПАРОЛЬ
gunzip db.gz && mv db data/giveaway.db
```

Проверено сквозной прогонкой: sha256 исходника и восстановленной базы совпадают,
с неверным паролем архив не открывается.

**Картинки постов (`data/uploads`, ~141 МБ) наружу НЕ уезжают** — бот не может
загрузить в Telegram файл больше 50 МБ. Остаётся дырой.

Локальные копии: база при каждом прогоне (раз в 6 ч, хранится 28), картинки —
**раз в сутки** и только 3 штуки. Раньше картинки паковались целиком каждые
6 часов, а лимит считался на все файлы разом: восемь одинаковых архивов по
140 МБ вытесняли маленькие копии базы, ради которых всё и затевалось.

## Логи

Режет `pm2-logrotate`: больше 10 МБ или в полночь. **Его собственное сжатие не
работает** — настройка сохраняется, файлы остаются текстовыми. Поэтому сжатие
и лимит архивов вынесены в `scripts/compress-logs.sh` (таймер
`giveaway-log-compress.timer`, раз в час). Лимит держится там же: pm2-logrotate
удаляет старое, узнавая свои файлы по имени, и после сжатия перестаёт их видеть.

Логи сжимаются примерно в 20 раз, так что не жалейте их: 11.6 МБ ужались до 1.25 МБ.

## Хранилище и гонки

SQLite используется как хранилище документов: одна строка = один JSON целиком
(`draws`, `draws-archive`, `user-project-profiles`, `projects`, `support-chats`, …).
Читается и пишется документ целиком — отсюда весь класс проблем.

**Классическая гонка здесь:** `readData()` → `await` (сеть) → `writeData(data)`.
За время `await` кто-то успел записать своё, и запись всё затирает. Так терялись
завершения розыгрышей и победители переигрывались заново.

Правила:

- **Всегда `writeDataPreservingLiveWinners(data)`**, никогда голый `writeData(data)`.
- Не держать документ в руках через сетевой вызов — сначала запрос, потом чтение и запись.
- Слияние в `src/winner-notify-sync.js` обязано **сохранять идентичность объектов**
  (`replaceContentsInPlace`): планировщик держит ссылки на массив и на конкретный розыгрыш
  и мутирует именно их. Замена объекта на новый = изменения уходят в пустоту.
- Решение по победителю выбирается так: выплата финальна → побеждает **более свежее**
  решение → ранг только как тайбрейк при полной ничьей.
- Отметки «когда последний раз смотрели» (`payoutQueueSubscriptionCheckedAt`) — это
  бухгалтерия, а не решение. Они переносятся на победивший объект по максимуму
  (`carryNewerCheckStamps`). Без этого проверка «раз в час» превращалась в проверку
  каждые 30 секунд для всех 159 победителей.

## Telegram

**Кэш подписки** (`src/subscription-cache.js`). Одно правило, ломать нельзя:
**запоминается только «подписан»**. Кэш отказа оставит человека, который только что
подписался и нажал «Я подписался», в тупике навсегда.
Проверки перед выплатой передают `fresh: true` и всегда идут в Telegram — там смысл
именно в свежем ответе, иначе заплатим отписавшемуся.

**Кэш ссылок на аватарки** (`src/file-link-cache.js`). Аватарка отдаётся редиректом
на файловую ссылку Telegram, и получение этой ссылки — отдельный запрос к API.
Ссылки живут около часа, поэтому TTL кэша (45 мин) **поднимать выше часа нельзя** —
отдадим протухшую. Семидневная проверка свежести прикрывает только запрос самой
фотографии, это разные вещи.

**Участие без доступа в личку не пропускается.** Если у человека нет
`allows_write_to_pm`, мини-апп просит разрешение через `requestWriteAccess`.
Кто идёт обходным путём («Открыть бота»), проверяется **на сервере**:
эндпоинт `/api/join/:drawId/notify-status` дёргает `sendChatAction` — он падает
с тем же 403, что и сообщение, но человеку ничего не показывает. Верить клиенту
на слово нельзя: он знает лишь намерение, а не факт. Раньше факт открытия бота
считался за разрешение, и люди участвовали в розыгрышах, о победе в которых бот
не смог бы им сообщить. Временный сбой сети трактуется как «достижим» —
не пускать живого человека хуже, чем пропустить недостижимого.

**Ошибки редактирования постов бывают вечными.** «message to edit not found»,
«there is no text in the message to edit», «MESSAGE_ID_INVALID», «bot was blocked» —
повторять бесполезно. Ставится метка, попытки прекращаются. Иначе получаются
бесконечные циклы: такое уже давало 1328 повторов на один пост.

**Синхронизация постов при старте** сравнивает отпечаток клавиатуры с тем, что
отправляли в прошлый раз, и молча пропускает неизменившиеся. Отпечаток берётся
**только с клавиатуры**: в тексте тикает обратный отсчёт, а в посте он обновляется
с задержкой, поэтому текст в отпечатке давал ложные расхождения на каждом запуске.

**Счётчик участников в посте** правится не чаще раза в минуту (throttle, не debounce),
иначе на активном розыгрыше правки идут потоком.

**Премиум-эмодзи** (`src/draw-post-emojis.js`) работают так: бот шлёт пост владельцу
в личку (там они разрешены, если у владельца есть Premium), владелец **пересылает**
в канал — сущности переживают пересылку. Напрямую в канал бот их слать не может:
для этого нужен коллекционный юзернейм с Fragment (~5000 TON доплаты). Не окупается.
Отката на обычные эмодзи при отказе Telegram **нет** — если Premium у владельца
кончится, посты перестанут отправляться.

## Планировщик

Завершает розыгрыши по таймеру и рассылает победителям. Тик — 30 секунд.

Историческая грабля: `await bot.launch()` **никогда не резолвится** при живом боте,
поэтому код после него не выполняется. Планировщик стартует в коллбэке `launch({}, cb)`
и, отдельно, до подключения — чтобы работать даже пока Telegram недоступен.
Обрыв связи (кроме 409) не должен глушить планировщик: сеть до Telegram с этого
сервера периодически моргает, это подтверждено замерами.

Строка `[boot] Telegram polling остановлен` — это **штатное выключение** по SIGTERM
при перезапуске, не поломка.

Признаки жизни: `data/.scheduler-heartbeat` (время, номер тика, счётчики вызовов
Telegram), сторож `scripts/watchdog.js` по systemd-таймеру, страница `/admin/system`
с кнопкой «скопировать отчёт».

## Тесты

```bash
npm test        # node --test src/*.test.js
```

Тесты не поднимают бота и не ходят в сеть — так и должно остаться.
`src/index.js` монолитный и не тестируется напрямую: логику, которую важно закрепить,
выносить в отдельный модуль рядом с тестом (так сделаны `subscription-cache`,
`winner-notify-sync`, `admin-*`).

Каждая починенная гонка или ошибка Telegram должна получить тест — иначе она вернётся.

## Стиль

- Комментарии в коде — английские, по существу: **почему** так, а не что делает строка.
  Особенно там, где очевидное решение неверно.
- Тексты для пользователей — русские.
- Секреты в репозиторий не попадают. В логах и отчётах админки токены вырезаются
  по форме (`src/admin-system.js`, `scrub`).
