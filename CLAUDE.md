# RollerBot — правила работы с проектом

Telegram-бот розыгрышей (`@roller_official_bot`) + мини-апп участия + веб-админка.
Прод: `/opt/giveaway-bot` на отдельном сервере, под pm2. Код — CommonJS, Node 20 на сервере.

Этот файл читается автоматически в начале каждой сессии. Здесь то, что **не видно из кода**:
запреты, грабли и договорённости. Всё остальное — в `README.md`.

---

## Запреты

**Не запускать бота локально.** `npm start`, `npm run dev`, `node src/index.js` — нельзя.
В локальном `.env` тот же `BOT_TOKEN`, что и на проде. Второй процесс с тем же токеном
вызывает у Telegram ошибку 409, и **боевой бот падает**. Это уже случалось.
Единственное исключение — тестовый бот, `npm run dev:test` (см. «Тестовый бот»).

**Не запускать `node --test src/`** (по каталогу) — подхватит лишнее и поднимет бота.
Только `npm test` или конкретные файлы: `node --test src/winner-notify-sync.test.js`.

**Не править код на сервере.** Сервер — чистая копия GitHub, пул только оттуда.
Ручная правка там потеряется при следующей выкатке и разведёт состояния.

**Не трогать в веб-админке ничего, кроме чтения.** Владелец делает все действия
через мини-апп; сайт — только статистика и поддержка. Единственное исключение:
в диалогах поддержки **должны** остаться ответ и завершение чата.

**Не писать пользователям.** Уведомления и тесты — только владельцу (`@timur_dollar`).

## Выкатка

```bash
npm test                                                      # локально, обязательно
git push origin main
ssh rollerbot 'bash /opt/giveaway-bot/deploy/update.sh'
```

С Windows то же самое делает `deploy-update.bat` (двойным кликом).

`update.sh` делает `git pull origin main` → `npm install --omit=dev` → `pm2 startOrRestart`.
GitHub — единственный источник правды для кода.

**Не в git и живёт только на сервере:** `.env` (токены), `data/giveaway.db` (вся база),
`data/uploads` (картинки постов), `backups/`.

## Сервер и доступ

`root@31.77.202.140` — Ubuntu 22.04, 1 vCPU, 2 ГБ RAM, 30 ГБ диска. Приложение
в `/opt/giveaway-bot`, файлы принадлежат пользователю `giveaway`, процессы под
pm2 от него же: **`sudo -u giveaway pm2 ...`** — от root список окажется пустым.

Три процесса: `giveaway-bot` (бот + веб + планировщик), `support-bot`,
`depman-support-bot`; плюс модуль `pm2-logrotate`.

Systemd-таймеры: `giveaway-watchdog` (3 мин), `giveaway-log-compress` (час),
`giveaway-backup` (6 ч), `giveaway-tg-backup` (3 ч).

nginx проксирует на `127.0.0.1:30009`, домен `rollerbot.pro`, сертификат от
certbot. **`deploy/nginx-giveaway-bot.conf` — только для первой установки.**
На сервере конфиг уже переписан certbot'ом; скопировать файл из репозитория
поверх — снести SSL.

**Приложение слушает только `127.0.0.1`** (`src/web-host.js`, переопределяется `WEB_HOST`).
Раньше оно слушало все адреса, а файрвола на сервере нет, поэтому порт 30009 отвечал
из интернета мимо nginx. При таком заходе заголовок `X-Real-IP`, которому верят антифрод
и лимит входа в админку (`src/client-ip.js`), мог подделать кто угодно.

**IP в `deploy/update-remote.local.ps1.example` устаревший** (`2.26.104.154`).
Актуальный — `31.77.202.140`.

## Работа с ПК (Windows)

Вход на сервер — по ключу `~/.ssh/id_ed25519_rollerbot`, алиас в `~/.ssh/config`:
`ssh rollerbot`. Пароль root не нужен нигде и в файлы не пишется.

`deploy/update-remote.local.ps1` (в .gitignore) заполнен с пустым паролем —
`deploy-update.bat` из-за этого идёт через `ssh` и ключ.

Локально Node 24, на сервере Node 20. `npm test` (210 тестов) проходит на обоих,
`better-sqlite3` ставится готовым бинарником, собирать нечего.

**Локального `.env` нет, и заводить его с боевым `BOT_TOKEN` нельзя** — см. запрет
в начале файла. Для вёрстки: `start-design.bat` → `npm run dev:design`, он читает
`.env` **и** `.env.design`, так что нужен `.env` с фиктивным `BOT_TOKEN` и настоящим
`BOT_USERNAME` (при `WEB_ONLY=true` без имени бота падает на старте).

## Тестовый бот

Второй бот со своим токеном, чтобы проходить изменения в настоящем Telegram
до выкатки. `npm run dev:test` читает **только** `.env.test` (образец в
`.env.test.example`): свой токен, `TEST_BOT=true`, своя база в `data-test/`
(`GIVEAWAY_DATA_DIR`). Оба файла в git не попадают.

Перед любым обращением к Telegram копия спрашивает, чей у неё токен
(`src/test-bot-guard.js`). Если это @roller_official_bot или не задана своя
папка данных, запуск останавливается.

Мини-аппу нужен https: к порту 3001 ведёт туннель (`cloudflared tunnel --url
http://localhost:3001`). Его адрес меняется при каждом запуске, поэтому новый
адрес надо прописать в `WEB_PUBLIC_URL` и в Mini App `join` у тестового бота
в @BotFather.

## Резервные копии

Локальные копии в `backups/` лежат на том же диске, что и база, — от смерти машины
не спасают. Поэтому каждые 3 часа зашифрованная копия базы уходит **в Telegram**
владельцу: `scripts/backup-to-telegram.js`, systemd-таймер `giveaway-tg-backup.timer`.

Снимок снимается через `db.backup()` (штатный онлайн-бэкап SQLite) — обычная
копия живого файла может порваться на середине записи. Шифрование обязательно:
в базе id пользователей, юзернеймы и TRC-20 кошельки, а нешифрованная копия в
чате — это копия в чужом облаке. Пароль лежит в `.env` (`BACKUP_PASSPHRASE`),
сгенерирован на сервере и **нигде не печатается**.

Восстановление не требует ничего из этого репозитория:

```bash
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -in ФАЙЛ -out db.gz -pass pass:ПАРОЛЬ
gunzip db.gz && mv db data/giveaway.db
```

Проверено сквозной прогонкой: sha256 исходника и восстановленной базы совпадают,
с неверным паролем архив не открывается.

**Картинки постов (`data/uploads`, ~360 МБ и растут) наружу НЕ уезжают** — бот не может
загрузить в Telegram файл больше 50 МБ. Остаётся дырой.

Локальные копии: база при каждом прогоне (раз в 6 ч, хранится 28), картинки —
**раз в сутки** и только 3 штуки. Раньше картинки паковались целиком каждые
6 часов, а лимит считался на все файлы разом: восемь одинаковых архивов по
140 МБ вытесняли маленькие копии базы, ради которых всё и затевалось.

## Логи

Режет `pm2-logrotate`: больше 10 МБ или в полночь. **Его собственное сжатие не
работает** — настройка сохраняется, файлы остаются текстовыми. Поэтому сжатие
и лимит архивов вынесены в `scripts/compress-logs.sh` (таймер
`giveaway-log-compress.timer`, раз в час). Лимит держится там же: pm2-logrotate
удаляет старое, узнавая свои файлы по имени, и после сжатия перестаёт их видеть.

Логи сжимаются примерно в 20 раз, так что не жалейте их: 11.6 МБ ужались до 1.25 МБ.

## Хранилище и гонки

SQLite используется как хранилище документов: одна строка = один JSON целиком
(`draws`, `draws-archive`, `user-project-profiles`, `projects`, `support-chats`, …).
Читается и пишется документ целиком — отсюда весь класс проблем.

**Классическая гонка здесь:** `readData()` → `await` (сеть) → `writeData(data)`.
За время `await` кто-то успел записать своё, и запись всё затирает. Так терялись
завершения розыгрышей и победители переигрывались заново.

Правила:

- **Всегда `writeDataPreservingLiveWinners(data)`**, никогда голый `writeData(data)`.
- **`read*Snapshot()` — только для чтения.** Разобранный документ общий для всех
  читателей, пока его не перезапишут (`src/document-snapshot.js`): изменишь его —
  изменишь у всех. Где документ правят и сохраняют, нужен обычный `readData()`.
  Снапшоты введены, когда опрос `/live` (раз в 2,5 с на каждый открытый экран
  «Готово») на каждый запрос разбирал профили на 3,3 МБ и держал ядро на 90%.
- **Не писать документ на каждый запрос.** Каждая запись — это чтение, разбор и
  сериализация документа целиком. `upsertUserMeta` стоит в проверке каждого
  запроса мини-аппа и раньше перезаписывал профили на каждом опросе `/live`;
  теперь пишет, только если имя поменялось или отметке больше 15 минут
  (`src/user-meta-touch.js`).
- Не держать документ в руках через сетевой вызов — сначала запрос, потом чтение и запись.
- Слияние в `src/winner-notify-sync.js` обязано **сохранять идентичность объектов**
  (`replaceContentsInPlace`): планировщик держит ссылки на массив и на конкретный розыгрыш
  и мутирует именно их. Замена объекта на новый = изменения уходят в пустоту.
- Решение по победителю выбирается так: выплата финальна → побеждает **более свежее**
  решение → ранг только как тайбрейк при полной ничьей.
- **Воронка вступления — отдельная таблица `join_funnel`, а не документ** (`src/join-funnel.js`).
  В ней одна строка на человека в розыгрыше, шаги записаны битами, строки живут 90 дней.
  Журнал каждого ответа раздул бы базу, а её целиком шлют бэкапом в Telegram, где лимит 50 МБ.
  Записывает перехватчик ответов join API. Параметры адреса он читает сразу: к моменту
  отправки ответа у маршрута уже свои `req.params`.
- Отметки «когда последний раз смотрели» (`payoutQueueSubscriptionCheckedAt`) — это
  бухгалтерия, а не решение. Они переносятся на победивший объект по максимуму
  (`carryNewerCheckStamps`). Без этого проверка «раз в час» превращалась в проверку
  каждые 30 секунд для всех 159 победителей.

## Telegram

**Кэш подписки** (`src/subscription-cache.js`). Одно правило, ломать нельзя:
**запоминается только «подписан»**. Кэш отказа оставит человека, который только что
подписался и нажал «Я подписался», в тупике навсегда.
Проверки перед выплатой передают `fresh: true` и всегда идут в Telegram — там смысл
именно в свежем ответе, иначе заплатим отписавшемуся.

**Кэш ссылок на аватарки** (`src/file-link-cache.js`). Аватарка отдаётся редиректом
на файловую ссылку Telegram, и получение этой ссылки — отдельный запрос к API.
Ссылки живут около часа, поэтому TTL кэша (45 мин) **поднимать выше часа нельзя** —
отдадим протухшую. Семидневная проверка свежести прикрывает только запрос самой
фотографии, это разные вещи.

**Сохранённый `file_id` аватарки умирает**, когда человек удаляет или меняет фото:
`getFile` отвечает 400 «wrong file_id». Списочная проверка людей с фото не смотрит,
поэтому мёртвый id жил вечно, и панель спрашивала о нём Telegram на каждой отрисовке.
Теперь запрос картинки сам заново берёт фото человека (`src/avatar-repair.js`) — не чаще
раза в 30 минут на человека и только на этот ответ Telegram, не на таймауты и 429.

**Пост розыгрыша уходит в канал rich-сообщением** (Bot API 10.3): кнопка «Участвую» внутри
поста, а не под ним. Сборка — `src/rich-post.js` (текст и entities наших же сборщиков
переводятся в rich HTML, второго варианта текста нет), отправка — `src/telegram-rich.js`
(telegraf 4.x этих методов не знает, вызовы идут прямо в HTTP API).

- **Ширины у кнопки в посте нет** — она ровно по длине подписи, в API только выравнивание.
  Поэтому подпись добита пробелами `　` под ширину телефона. Шире — Телеграм обрежет
  подпись многоточием.
- **Премиум-эмодзи в канальные посты не идут** (решение владельца) — только в личку.
- **Обложка загружается один раз**, дальше правки счётчика шлют `file_id` (`draw.coverFileId`).
- **Старые посты** (`messageType` `photo`/`text`) правятся по-старому: выбор по типу, не по флагу.
- **Пост-напоминание** (`src/draw-digest-rich.js`) тоже rich: каждый розыгрыш — зелёная кнопка
  вместо строки с «КЛИК», строк «Призовых мест / Итоги через» в нём больше нет. Как отправлен
  каждый дайджест, помнит поле `rich` в `activeDrawsDigestReminders` — старые правятся по-старому.
- **Старые версии Телеграма такой пост не отрисуют** — показывают заглушку «откройте Telegram».
  Откат без выкатки: `DRAW_POST_RICH=false` в `.env` + рестарт, новые посты снова обычные.

**reCAPTCHA на проде не включена**: ключей в `.env` нет, работает своя галочка. С секретом
сервер принимает только ответ Google (`src/join-captcha.js`). Если у человека не загрузится
скрипт Google, мини-апп покажет свою галочку, а сервер с секретом её не примет, и человек
застрянет. Прежде чем включать reCAPTCHA, решить, что делать с такими людьми.

**Участие без доступа в личку не пропускается.** Если у человека нет
`allows_write_to_pm`, мини-апп просит разрешение через `requestWriteAccess`.
Кто идёт обходным путём («Открыть бота»), проверяется **на сервере**:
эндпоинт `/api/join/:drawId/notify-status` дёргает `sendChatAction` — он падает
с тем же 403, что и сообщение, но человеку ничего не показывает. Верить клиенту
на слово нельзя: он знает лишь намерение, а не факт. Раньше факт открытия бота
считался за разрешение, и люди участвовали в розыгрышах, о победе в которых бот
не смог бы им сообщить. Временный сбой сети трактуется как «достижим» —
не пускать живого человека хуже, чем пропустить недостижимого.

**Бот сам (`/start`, старая кнопка `join:`) пускает без шагов только тех, кого пустил бы
мини-апп**, по тем же правилам `decideJoinEntry`: подписка на канал, доступ в личку, ID.
Раньше розыгрыш без проекта и сохранённый профиль проходили там мимо капчи и канала.

**Автовход тоже ждёт этого ответа.** Кто уже участвовал в розыгрышах проекта,
добавляется в новый сразу при открытии мини-аппа (`/session`). Раньше ответ «бот
не может написать» только помечал ответ для клиента, а человека уже добавили.
Теперь такой человек идёт обычным путём: «откройте бота» → капча → участие
(`src/join-entry-decision.js`).

**Ошибки редактирования постов бывают вечными.** «message to edit not found»,
«message was deleted» (так отвечает удалённый rich-пост),
«there is no text in the message to edit», «MESSAGE_ID_INVALID», «bot was blocked» —
повторять бесполезно. Ставится метка, попытки прекращаются. Иначе получаются
бесконечные циклы: такое уже давало 1328 повторов на один пост.

**Синхронизация постов при старте** сравнивает отпечаток клавиатуры с тем, что
отправляли в прошлый раз, и молча пропускает неизменившиеся. Отпечаток берётся
**только с клавиатуры**: в тексте тикает обратный отсчёт, а в посте он обновляется
с задержкой, поэтому текст в отпечатке давал ложные расхождения на каждом запуске.

**Правки одного поста идут по очереди** (`src/post-edit-queue.js`). Пост розыгрыша правят
три независимых места: обновление после вступления, обратный отсчёт и догонялка счётчика.
Когда две правки сходились, Telegram отменял первую («canceled by new edit message request»).
Любая новая правка сообщения в канале должна идти через `runDrawPostEdit`.

**Счётчик участников в посте** правится не чаще раза в минуту (throttle, не debounce),
иначе на активном розыгрыше правки идут потоком.

**429 на правке поста выжидается**: сколько Telegram сказал в `retry_after`, до 20 с,
не больше двух повторов (`src/telegram-flood-retry.js`, внутри `withTelegramEditTimeout`).
Только правки постов — сообщения людям и проверки внутри веб-запросов должны
падать быстро, а не висеть.

**Премиум-эмодзи** (`src/draw-post-emojis.js`) работают так: бот шлёт пост владельцу
в личку (там они разрешены, если у владельца есть Premium), владелец **пересылает**
в канал — сущности переживают пересылку. Напрямую в канал бот их слать не может:
для этого нужен коллекционный юзернейм с Fragment (~5000 TON доплаты). Не окупается.
Отката на обычные эмодзи при отказе Telegram **нет** — если Premium у владельца
кончится, посты перестанут отправляться.

## Бренды и проекты

Проекты руками не создаются — это фиксированные бренды из
`BRAND_PROJECT_TEMPLATES` (`src/deposit-guide.js`): Pokerdom, BEEF, FUGU, IRIS,
LuckyBear. Каждый организатор получает свою копию при следующем открытии панели
и сам вписывает реф-ссылку, эмодзи и промокод.

**`templateSlug` менять нельзя никогда** — он входит в id проекта
(`brand_<slug>_<ownerId>`), а эти id уже записаны в розыгрышах и профилях.
Старые, добрендовые id не потеряны: `src/project-identity.js` разводит их на
нынешние. Без этого панель показывает «Проект удалён» и половину истории человека.

**Проверка ID отказывает только в том, чего проект выдать не мог** (`src/project-account-id.js`).
Строгая маска LuckyBear, написанная по одному скриншоту, когда-то отказала пятнадцати
живым людям подряд. Не пустить настоящего участника дороже, чем пропустить
странный id: дубли и антифрод отработают после. Поэтому правила сняты с реальных данных:
LuckyBear — числовой UID из профиля (подтвердил владелец), Pokerdom — ровно 24 hex-символа
(MongoDB ObjectId), #XXXXX — отказ только ID из одного-двух разных символов, рядов
клавиатуры и стоп-листа имён и слов. 44% настоящих #XXXXX состоят из одних букв, так что
запрещать буквы нельзя.

**Аккаунт Pokerdom, созданный до 1 июня 2026 (МСК), рефералом не считается**: владелец
начал набирать рефералов с этого дня. Дату хранят первые 8 символов ID. При вводе такой
человек помечается не-рефералом, что бы ни выпало случайно.

**Сохранённый ID, который не проходит нынешнюю проверку** (#SLAVA, e-mail, ссылка),
шагом не считается, и в следующем розыгрыше шаг с ID показывается снова. Базу при этом
не переписывают: это решает `hasCompletedProjectIdStep`, когда ему передан проект.

**Статус реф / не реф подтверждается скриншотом профиля** (решение владельца). Шаг «Регистрация»
у всех розыгрышей с проектом: «зарегистрированы по ссылке стримера?» → скрин профиля → «Ваш ID на … —
верно?». Скрин читает gemini-2.5-flash через OpenRouter (`src/profile-shot-reader.js`): бренд и ID.
flash-lite для бренда не годится — на скринах владельца назвала BEEF «FUGU» с уверенностью 0.9.
BEEF, FUGU и IRIS на мобильной версии без логотипа, бренд различается по оформлению, **не по уровням**
(владелец запретил: уровни у всех свои). ID всё равно проходит проверку формата бренда. Правила
(`src/join-profile-shot.js`):

- база начинается заново: первый скрин ставит **железный** статус `verifiedStatus`, который потом
  не меняет ничто — ни новые скрины, ни кошелёк с историей (шаг кошелька и запрос адреса у победителя
  его не трогают). До первого скрина действует старый статус;
- скрин спрашивается раз в неделю, вопрос «реферал?» — только при первом;
- «Я не зарегистрирован» остаётся и при скрине: показать нечего, участие с меткой «Не зареган»,
  в следующий раз вопрос снова;
- розыгрыш «Только для рефов» (`draw.refOnly`) **никого с аккаунтом не отказывает** (решение владельца):
  «не реф», подтверждённый «не реф» и человек другого организатора бренда входят как «не реф» после того
  же скрина, «чужой» помечается чужим рефом. В нём нет «Я не зарегистрирован» и жребия «20% не реф».
  Раньше «не реф» там отказывали, и это учило отвечать «реф»: в первом таком розыгрыше 17 из 29
  участников раньше сами говорили этому организатору «не реф». С «Просить ID с проекта» не совмещается;
- «не реф» со скрином тоже проверяется на «хозяина» бренда, чтобы в панели было видно, чей он реферал.

Скрины лежат в `data/profile-shots` (в бэкап не уезжают) и видны только в веб-админке, в карточке
человека. Сохраняется скрин только после «Да, это мой ID». Телефон ужимает его до 1400 px перед
отправкой. Откат без выкатки: `JOIN_PROFILE_SHOT=false` в `.env` + рестарт — участие снова с вводом ID.
Копия базы до перехода: `backups/manual/before-profile-shot-*.db`.

**Один бренд — один «хозяин».** Рефералом человек может быть только у того организатора,
у которого первым участвовал в этом бренде: смотрится самое раннее участие по всем розыгрышам,
включая архив. У остальных организаторов этого бренда он «не реф» (`crossOrganizerNonReferral`)
и проходит в их розыгрыши без шагов, с данными от первого. Правило задаёт `findBrandHomes`
(`src/project-profile-bridge.js`), и его соблюдают все три места, где ставится статус: жребий,
шаг ID и шаг кошелька. Раньше человек мог стать рефом у второго организатора через шаг
кошелька или жребий — так было у 44 человек. Старые двойные «реф» при каждом запуске снимает
`src/brand-home-backfill.js`; тех, кто ждёт выплату у этого организатора, он пока не трогает.

## Рефералы

Разделитель в `startapp` — `-ref-` (`src/join-referrals.js`). `__ref__` и `_ref_`
разбираются только ради ссылок, уже гуляющих по рукам; заново их использовать
нельзя — по дороге съедались подчёркивания и ссылка не совпадала ни с одним
розыгрышем.

**Буст за приглашения — чисто визуальный.** Реальный шанс это
`winnersCount / participantCount`; `referralBoostPercent` в розыгрыш не входит.
Это решение, а не недоделка.

## Поддержка

Два отдельных процесса на общем движке `src/create-support-bot.js`:
`support-bot` (@rollerbot_support_bot) и `depman-support-bot` (VIP стримера,
@depman_support_bot). Различаются промптом (`support-ai.js` /
`depman-support-ai.js`) и текстами.

Модели идут цепочкой (`src/support-models.js`): при 429, таймауте или снятой
модели берётся следующая, и последняя в цепочке — **у другого провайдера**,
чтобы лимит Google не выключил поддержку целиком. Модели, которые выдумывали
факты («вижу по базе твою победу» — базы у них нет), выброшены осознанно.
Не возвращать.

**Внутри обработчика Telegraf нельзя ждать долго.** Telegraf не берёт новые сообщения, пока не
обработал те, что уже взял, и через 90 секунд бросает `TimeoutError`. Ночной «поиск оператора»
в поддержке длится 3–7 минут и раньше ждался прямо в `/start`, поэтому вся поддержка замирала
на полторы минуты для всех. Теперь поиск идёт отдельно (`runOperatorSearch`), а то, что человек
пишет во время поиска, ждёт приветствия.

У прокси к OpenRouter (`OPENROUTER_PROXY_URL`) свой предохранитель: он виснет
примерно на четырёх запросах из десяти, поэтому после трёх неудач подряд запросы
пять минут идут напрямую (`src/openrouter-fetch.js`).

## Лендинг rollerbot.pro

Главная страница — `src/landing-page.js`, выбранный владельцем вариант «Классика» в духе
Apple и Telegram: iPhone с Telegram внутри вместо иконок, логотипы партнёров в сером. Интерфейс
панели и админки на лендинге не показывается, только сторона участника.

Демо в телефоне на первом экране крутится по кругу. Так попросил владелец, хотя в
мини-аппе бесконечные анимации убраны. Демо идёт только пока телефон на экране и вкладка открыта.
Остальные анимации проигрываются один раз.

Если корень сайта открыт как Mini App (есть `tgWebAppStartParam`), сервер переводит в участие
(`src/root-mini-app-redirect.js`).

## Панель организатора

Разметку карточек, статистики и очереди выплат собирает `src/index.js`, вид — `src/panel-look.js`
(стили и маленький клиентский скрипт: фильтры, таймеры, досчёт цифр), числа и даты —
`src/panel-format.js`. Все новые классы начинаются с `pl-`.

**Своя кнопка в панели ловит старые правила.** В `index.js` и `miniapp-ui.js` есть цепочки
`button:not(.a):not(.b)…` — базовый вид кнопок и слой тиснения с `!important`. Специфичность такой
цепочки выше любого обычного правила, поэтому кнопку с собственным видом добавляют `:not(.класс)`
в каждую цепочку (так сделано для `.pl-seg-btn`), иначе у неё синий фон и тень.

**Опрос `/panel/live` заменяет карточки целиком** (`outerHTML`, поиск по `.pl-card[data-draw-id]`).
Обработчики на карточках — только делегированием на `document`: у карточек из «Показать ещё»,
фильтра и опроса своих обработчиков нет. Так розыгрыши удалялись без подтверждения.

**Внутри карточки документы не читаются.** Всё, что нужно карточке победителя, читается один раз
на страницу и передаётся в неё (`createPanelRenderReads`, `src/panel-referral-badge.js`).
Метка «Реф» раньше разбирала профили (3,5 МБ) на каждую карточку — панель открывалась ~10 секунд.

**`?v=<сборка>` ставит сервер** (`src/panel-build-redirect.js`) редиректом до отрисовки. Скрипт
в `<head>` делает то же самое, но только после того, как страница уже нарисована, — каждое
открытие стоило двух отрисовок. Скрипт оставлен: он ловит страницу из кэша WebView.
Правило «перезагружать ли» у сервера и скрипта одно, тест это сверяет.

**Метка «Реф …» подписывает чужого реферала именем, которое владелец дал админу** в «Доступе»
(поле «Имя», карандаш у админа), и только без него — именем из Telegram или @username
(`src/admin-label.js`). Так попросил владелец.

**«Написать» у победителя** открывает чат с ним. С username это просто `t.me/<ник>`. Без username
мини-апп чат не откроет: `openTelegramLink` принимает только ссылки t.me, а голая `tg://user?id`
открывается лишь там, где клиент уже знает человека. Поэтому бот присылает организатору кнопку
`tg://user?id` (её Telegram гарантирует для тех, кто писал боту), и панель переводит в чат с ботом
(`src/winner-chat-link.js`). Если человек запретил ссылки на себя, Telegram отказывает
(`BUTTON_USER_PRIVACY_RESTRICTED`), и панель так и говорит. Профиль участника открывается
с аватарки. Под логотипом бренда показан ID, который человек оставил проекту, красным, если он
не может быть настоящим (`src/winner-account-id.js`). Длинный ID Pokerdom сокращён до `6a2e…443d`
и раскрывается нажатием; копировать ID владелец не просил.

**Эмодзи-пикер заголовка** (`src/emoji-picker.js`) раскрывается в форме, а не всплывает поверх:
всплывашке доставался остаток места под полем, и в ней было видно два ряда. Все ~1900 эмодзи
лежат в `assets/emoji/emoji-data.json`, файл собирает `scripts/build-emoji-data.js` из
emojibase-data (в зависимости её нет, как пересобрать — в шапке скрипта). Эмодзи новее Unicode 15
не берутся: на телефоне пару лет назад они видны пустыми квадратами. Файл отдаётся по
`/emoji/data.json?v=<хэш>` уже сжатым и кэшируется навсегда. Стили пикера стоят **после**
стилей планера, вне фильтра раскладки: пропущенные через него, они теряют шрифт эмодзи.
Поиск (`src/emoji-search.js`) понимает формы слова, неверную раскладку и одну опечатку, но
пробует их только когда точного совпадения нет. Иначе на каждый запрос лез шум.

## Веб-админка

Вид админки — в языке планера и мини-аппа (шрифт и палитра iOS, стеклянные карточки,
светлая и тёмная тема). Устройство:

- `src/admin-ui.js` — каркас, токены и компоненты;
- `src/admin-charts.js` — графики, свои SVG и HTML, без библиотек и без внешних скриптов;
- `src/admin-pages.js` — сами страницы;
- `src/admin-dashboard.js` — данные и маршруты.

Подписи в подсказках графиков собираются через `textContent`, не через HTML.

Смотреть админку локально — на выдуманной базе: `GIVEAWAY_DATA_DIR=data-design node
scripts/seed-admin-design.js`, в `.env.design` указан тот же `GIVEAWAY_DATA_DIR`. Настоящих
людей там нет, и ни у кого нет аватарки, поэтому админка не ходит в Telegram с боевым токеном.
После пересоздания базы дизайн-сервер нужно перезапустить: он держит открытым старый файл.

## Страницы участника

**Профиль `/user/<id>` открывает любой, у кого есть ссылка.** Поэтому «Мои розыгрыши»
в страницу не встроены: список отдаёт `/api/me/draws` и только по подписи Telegram,
для того человека, который в ней указан. В список попадают и анонимные участия.
Свою строку «Вы» на экране «Готово» может открыть каждый, чужие профили открывает
только админ.

**Значения во встроенный `<script>` вставляются только через `scriptJson`**
(`src/script-json.js`). `JSON.stringify` не экранирует `</script>`: id из адреса профиля
выполнялся как код страницы на rollerbot.pro. В адресе профиля принимаются только цифры,
в `?back=` — только путь этого сайта.

## Планировщик

Завершает розыгрыши по таймеру и рассылает победителям. Тик — 30 секунд.

Историческая грабля: `await bot.launch()` **никогда не резолвится** при живом боте,
поэтому код после него не выполняется. Планировщик стартует в коллбэке `launch({}, cb)`
и, отдельно, до подключения — чтобы работать даже пока Telegram недоступен.
Обрыв связи (кроме 409) не должен глушить планировщик: сеть до Telegram с этого
сервера периодически моргает, это подтверждено замерами.

Строка `[boot] Telegram polling остановлен` — это **штатное выключение** по SIGTERM
при перезапуске, не поломка.

Признаки жизни: `data/.scheduler-heartbeat` (время, номер тика, счётчики вызовов
Telegram), сторож `scripts/watchdog.js` по systemd-таймеру, страница `/admin/system`
с кнопкой «скопировать отчёт».

## Тесты

```bash
npm test        # node --test src/*.test.js
```

Тесты не поднимают бота и не ходят в сеть — так и должно остаться.
`src/index.js` монолитный и не тестируется напрямую: логику, которую важно закрепить,
выносить в отдельный модуль рядом с тестом (так сделаны `subscription-cache`,
`winner-notify-sync`, `admin-*`).

Каждая починенная гонка или ошибка Telegram должна получить тест — иначе она вернётся.

## Стиль

- Комментарии в коде — английские, по существу: **почему** так, а не что делает строка.
  Особенно там, где очевидное решение неверно.
